# Fuel privacy audit — 2026-10-22

Scope: source review of `origin/main` at `c598d24`. Product rule 7 requires meal logs and measurements to stay on device until backup is chosen, and forbids health data in analytics (`origin/docs/fuel-v2-spec:fighter_edge/docs/FUEL_V2_SPEC.md:43-44`). Slice N6 asks for local-first storage, a separate backup consent, and an analytics scrub (`origin/docs/fuel-v2-spec:fighter_edge/docs/FUEL_V2_SPEC.md:139-144`). The research proposes local storage by default and a separate backup toggle (`origin/docs/fuel-v2-spec:fighter_edge/docs/nutrition_research_20261022/retention.md:124-129`). All paths below are relative to the repository root. This is a code audit, not a check of live user data.

## Five findings, ranked by risk

1. **High — Meal logs and weights go to Firestore now.** Each day save sends entries and nutrient totals to `users/{uid}/nutritionDays/{dateKey}`; the older meal flow and weight tracker also write to Firestore. No separate backup choice exists (`fighter_edge/lib/features/edge_fuel/data/firestore_edge_fuel_repository.dart:118-128`; `fighter_edge/lib/data/firestore_data_repository.dart:34-36,54-63`; `fighter_edge/lib/privacy/data_consent.dart:10-18`).
2. **High — The setup draft syncs before confirmation.** Every field setter saves the full draft, including weight, body fat and clinical flags, before the user taps Confirm. The app asks for general health-data consent first, but this is not optional backup consent (`fighter_edge/lib/features/edge_fuel/presentation/controllers/edge_fuel_setup_controller.dart:50-55,107-111,123-134`; `fighter_edge/lib/features/edge_fuel/domain/models/nutrition_setup_draft.dart:153-173`; `fighter_edge/lib/screens/onboarding/onboarding_screen.dart:90-93`).
3. **High — Firestore enforces ownership, not backup consent.** Another signed-in user cannot read these paths, but the owner can write nutrition and weight documents even without a `healthData` record; no backup purpose is allowed yet (`fighter_edge/firestore.rules:18-23,47-56,87-89,107-116`).
4. **Medium — Some analytics events describe health behavior.** The allow-list blocks raw measurements, meal text, email and UID parameters, but it permits a weight-loss goal, training frequency, and a meal-log occurrence flag. These conflict with rule 7's broad “no health data in analytics events” wording (`fighter_edge/lib/observability/telemetry.dart:10-12,201-225`; `fighter_edge/lib/screens/onboarding/onboarding_screen.dart:251-259`; `fighter_edge/lib/features/edge_fuel/presentation/controllers/edge_fuel_controller.dart:164-170`; `origin/docs/fuel-v2-spec:fighter_edge/docs/FUEL_V2_SPEC.md:43-44`).
5. **Medium — Local copies need a deletion and iOS backup check.** Firestore disk persistence is enabled; a separate SharedPreferences index holds full recent and saved food entries. The account deletion function removes the server tree, while the client flow signs out without an explicit local purge. Android backup exclusions are present; no iOS exclusion or file-protection setting was found in the inspected project files (`fighter_edge/lib/main.dart:153-155`; `fighter_edge/lib/features/edge_fuel/presentation/controllers/food_memory.dart:24-45,95-104`; `fighter_edge/functions/src/accountDeletion.ts:39-44`; `fighter_edge/lib/auth/firebase_auth_repository.dart:391-409`; `fighter_edge/android/app/src/main/AndroidManifest.xml:28-36`; `fighter_edge/android/app/src/main/res/xml/data_extraction_rules.xml:7-21`; `fighter_edge/ios/Runner/Info.plist:1-45`).

## 1. Firestore paths and fields

“Health” marks data to treat as health or health-adjacent under the product rule. A field marked “No, linked” is ordinary metadata in a health document, so it still needs the same protection. The current app shows health consent before onboarding and again to older accounts (`fighter_edge/lib/screens/onboarding/onboarding_screen.dart:90-93`; `fighter_edge/lib/screens/auth/auth_gate.dart:42-46`). The repository methods and subcollection rules do not check that consent, and there is no separate backup opt-in (`fighter_edge/lib/features/edge_fuel/data/firestore_edge_fuel_repository.dart:63-70,83-87,118-128`; `fighter_edge/firestore.rules:18-23,47-56`; `fighter_edge/lib/privacy/data_consent.dart:10-18`). The server's recursive account deletion covers all listed `users/{uid}` documents when it succeeds (`fighter_edge/functions/src/accountDeletion.ts:34-44`).

The profile and target watchers read the saved document through their model `fromJson` methods (`fighter_edge/lib/features/edge_fuel/data/firestore_edge_fuel_repository.dart:53-79`; `fighter_edge/lib/features/edge_fuel/domain/models/nutrition_setup_draft.dart:176-205`; `fighter_edge/lib/features/edge_fuel/domain/models/nutrition_target.dart:103-132`). The day watcher reads the day fields listed below, except the currently unused `schemaVersion`, `hydrationCheckIns` and `activitySnapshot` placeholders (`fighter_edge/lib/features/edge_fuel/data/firestore_edge_fuel_repository.dart:91-100,176-187`; `fighter_edge/lib/features/edge_fuel/domain/models/nutrition_day.dart:72-114`). Entry reads also accept old `protein`, `carbs`, `fats` and `eaten` keys as aliases; entry `schemaVersion` is written but not parsed (`fighter_edge/lib/features/edge_fuel/domain/models/food_log_entry.dart:62-91`).
